# Publish three packages to npm with Changesets, shipping source, with a manual-gated "Version Packages" PR

Date: 2026-11-17 · Task: community release preparation

## Context

The monorepo is being prepared for a community release (MIT, `github.com/zawoj/emdash-commerce`; a community project for
EmDash, not an official one). Three packages are meant for other people: `@emdash-commerce/plugin-stripe`,
`@emdash-commerce/plugin-image-hotspots` and `@emdash-commerce/design-system`. Until now they were `private: true`
workspace packages consumed by `apps/storefront` only, with hard-coded plugin version constants and a hand-written root
`CHANGELOG.md`.

The reference is how EmDash (`emdash-cms/emdash`) and Cloudflare (`cloudflare/workers-sdk`) do it: Changesets with
`@changesets/changelog-github`, a `release.yml` on push to `main` with pinned actions and npm provenance, and first-party
plugins such as `@emdash-cms/plugin-forms` that ship TypeScript source (`main: src/index.ts`, `files: ["src"]`) which the
site's Astro and Vite build compiles.

## Decision

- **Changesets** (`@changesets/cli` 3, `@changesets/changelog-github`) in `.changeset/`, configured like EmDash's:
  `baseBranch: main`, `access: public`, `updateInternalDependencies: minor`, `bumpVersionsWithWorkspaceProtocolOnly`,
  and `ignore: ["@emdash-commerce/storefront"]` (the private demo). Root scripts `changeset`, `version`
  (`changeset version`) and `release` (`changeset publish`). Every package versions independently (no `fixed` group: the
  three have unrelated cadences). `.changeset/README.md` is the contributor guide; it adapts EmDash's.
- **Two changelogs, on purpose.** The root `CHANGELOG.md` stays the hand-written history of the monorepo and the demo
  storefront (what changed in the repo and why, including work that no package user needs to know). Each package's
  `CHANGELOG.md` is generated by Changesets from the changeset files and is what a package user reads. Folding them into
  one would either bury package users in demo changes or drop the demo history that `.ai/README.md` requires per PR.
- **Ship source, like `@emdash-cms/plugin-forms`.** The three packages already export `.ts`, `.tsx`, `.astro` and `.css`
  from `src`; they keep doing so, with no build step. `files` lists exactly what a consumer needs: `src` minus
  `*.test.ts(x)`, `*.contract.ts`, `test-support.ts`, `src/testing/fixtures` and the real-host test harness (the
  `./testing` export of `plugin-stripe` imports none of them, checked below), plus the README, `LICENSE`, `CHANGELOG.md`,
  `docs` (`plugin-stripe`) and the two lint scripts (`design-system`). `peerDependencies` replace exact links:
  `emdash`/`astro` for `plugin-stripe`, `emdash`/`@emdash-cms/admin`/`react`/`react-dom` for the widget, `astro` `^7` for the
  design system. `publishConfig` is `{ access: "public", provenance: true }`.
- **Plugin versions come from `package.json`.** `PLUGIN_VERSION` in both plugins was a literal that a version bump would
  leave stale (EmDash reads the plugin version from the definition, not from `package.json`). It is now
  `packageJson.version` (a JSON import), and a test in each plugin pins the equality.
- **Release workflow**: `.github/workflows/release.yml` on push to `main`, guarded by
  `github.repository == 'zawoj/emdash-commerce'`, default-deny `permissions` with `contents: write`, `pull-requests: write`
  and `id-token: write` on the one job, actions pinned to full commit SHAs, the gate run before anything is published, and
  `changesets/action` (the single-job form: a pending changeset opens or updates the "chore: version packages" PR; its merge
  publishes). Publishing uses the `NPM_TOKEN` repository secret and npm provenance. Merging the version PR is the human
  gate.
- **First release**: one `minor` changeset for all three. That makes the first public versions `plugin-stripe` 0.3.0,
  `plugin-image-hotspots` 0.2.0 and `design-system` 0.1.0, because the packages already carried 0.2.0, 0.1.0 and 0.0.1
  locally and a changeset cannot publish a version that is already in `package.json`.
- **No `emdash-plugin.jsonc`.** See the finding below.

### The EmDash plugin manifest (`emdash-plugin.jsonc`): not applicable

EmDash's `emdash-plugin` CLI (`packages/plugin-cli`) validates a manifest against
`schemas/emdash-plugin.schema.json`; its required fields are `slug`, `license`, `publisher`, `capabilities`,
`allowedHosts` and `storage`, and `publish` writes signed records to an atproto repository for the plugin registry
(`registry.emdashcms.com`). Reading the schema and the docs (`plugins/overview`, `plugins/creating-native-plugins/distributing`):

- **The registry is for sandboxed plugins only.** The distributing guide says it outright: "Native packages cannot be
  published to the EmDash registry." A plugin needs to be native when it has React admin pages, Portable Text rendering
  components, page fragments or direct access to the site process.
- `image-hotspots` has a React admin entry (`admin.entry`, a field widget): native by definition.
- `stripe-commerce` ships an Astro block component (`componentsEntry`, `src/astro/Product.astro`), reads and writes the
  database in-process through `emdash/runtime` (`getDb`), and registers a `hooks.content-policy` hook: native too. Its
  Block Kit admin page, routes, cron task and storage would fit a sandbox, but the component and the in-process database
  access do not.
- A manifest would also need a `publisher`, an atproto DID of a registry account the maintainers have not created;
  inventing one would be a fabricated identity.

So no manifest was added and none could be validated. Both plugins are distributed on npm as native plugins, which the
READMEs say. What would change this: splitting `stripe-commerce` into a sandboxed core (catalog, checkout, webhooks over
the sandbox's declared `network:request` host `api.stripe.com`) and a native storefront companion, once EmDash's sandbox
exposes what the plugin needs (relations, content-policy hooks). That is a redesign, not release mechanics.

## Alternatives

- **`nx release`.** The repo already uses Nx, and `nx release` can version, changelog and publish. Rejected: Changesets
  puts the release note in the pull request that makes the change (reviewed with it), which is what EmDash and Cloudflare
  do, and the contributor guidance, bot and GitHub Action ecosystem exist. `nx release` derives bumps from commit messages
  or prompts for them, and its changelog is not reviewed per PR. Nx stays the task runner.
- **Build to `dist` before publishing** (tsdown, as EmDash does for `emdash` itself and its sandboxed plugins). Rejected
  for now: both plugins import `.astro`, `.tsx` and `.css` that only the site's Vite build can compile, EmDash's own
  `plugin-forms` ships source for the same reason, and a build step would add a second place for exports to drift from the
  source. Revisit if a consumer needs compiled JavaScript.
- **One changelog.** Rejected (above).
- **Fixed or linked versions across the three packages.** Rejected: unrelated cadence; the design system and the widget
  have no dependency on the plugin.
- **A `scripts/` sync of the plugin version constants** after `changeset version`. Rejected for a JSON import: one
  source, no step to forget.
- **Reset the three versions to 0.0.0 so the first release is 0.1.0 everywhere.** Rejected: it rewrites the versions
  already cited in the READMEs and the plugin changelog for no consumer benefit. The maintainers can still change the
  numbers in the changeset before the first release.

## What was checked

Tarballs built with `pnpm pack` from each package (`plugin-stripe` 229 files, `plugin-image-hotspots` 23, `design-system` 463):

- `npx publint --pack pnpm --strict` reports "All good!" for all three.
- A closure script over the extracted tarball resolves every relative import of every packed source file (`.ts`, `.tsx`,
  `.astro`, `.css`, `.mjs`; 1049, 52 and 1306 imports) and every `exports`, `bin` and `main` target: nothing unresolved.
  Deleting one file from a tarball makes it fail, so it does catch a missing file.
- The three tarballs plus `emdash` 1.5.0, `@emdash-cms/admin` 1.5.0, `astro` 7.3.2, `react` and `react-dom` 19.2.3 were
  installed with `npm` into an empty project outside the repository (no peer warnings). Every TypeScript export was bundled with
  esbuild through the package `exports` map and imported in Node: `plugin-stripe` `.`, `./contracts`, `./testing`;
  `plugin-image-hotspots` `.`, `./admin`, `./value`; the `design-system` utility subpaths (with a happy-dom DOM for the
  browser scripts). `design-system/balanced-clamp` bundles but needs `document.fonts`, which happy-dom lacks, so it was
  not executed. The `.astro` and `.css` targets were checked as files and by Node's `exports` resolution.
- An Astro 7 `astro build` of a page using `Button` and the token CSS from the installed design system succeeded with no
  `vite.ssr.noExternal`. An EmDash 1.5 site (`@astrojs/node`, `@astrojs/react`) registering both plugins and the stripe
  `componentsEntry` from the tarballs built with no `noExternal` and no `@emdash-cms/admin` alias; the server bundle
  contains the plugin code and the client bundle the hotspots admin entry. The built server was not started and no request
  was made.

Not checked: publishing (never run), an install with pnpm (the scratch project used npm because the global pnpm shim
outside the repo is broken here), TypeScript type-checking of a consumer against the shipped `.ts` sources, Astro 6 with
the design system, and Node versions other than 24.22.1.

## Consequences

- A PR that changes a published package carries a changeset; the root `CHANGELOG.md` entry is still required for every PR.
- The first push to `main` after this lands opens a "Version Packages" PR. **The npm organization `@emdash-commerce` must
  exist and be owned by the maintainers, and the three names must be free, before that PR is merged.** This was not
  checked and nothing in the repository creates it. The `NPM_TOKEN` secret must be added by a maintainer (no value is in the
  repository). If either is missing the publish step fails and nothing is released.
- A PR opened by the default `GITHUB_TOKEN` does not trigger `ci.yml`. Either use a GitHub App token for the action, as
  EmDash does, or push to the version branch by hand to run CI. See `docs/releasing.md`.
- Consumers get TypeScript, React and Astro source and compile it in their own build. Peer ranges are the supported
  environment: `emdash ^1.5.0`, Astro 7 for the design system; Node `>=22.16.0` is copied from `emdash`'s `engines` and
  only Node 24.22.1 is exercised in this repository.
- The tarballs, not the repository, are what ships: `files` must be kept in step with `exports`. Verification is in
  `docs/releasing.md` (pack, install into a clean project, resolve every export) and the closure check described in
  `.ai/runs/2026-11-17-release-mechanics.md`.
